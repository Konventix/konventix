# General

## PHPStan needs --memory-limit=1G; tests/ is out of scope
Run it as `composer types:check` — plain `phpstan analyse` dies at PHP's default 128M with a misleading "Unable to load dynamic library phpstan_turbo" warning. The turbo extension is a red herring; the memory limit is the actual cause.

`tests/` is deliberately not in `paths`. Pest's higher-order `TestCall` chain is invisible to PHPStan without `pestphp/pest-plugin-phpstan`, so scanning tests yields only false positives. Add the plugin first if you want the coverage.

## `.env` must exist before the first `sail up`, or the pgsql volume is poisoned
compose.yaml passes `${DB_USERNAME}`/`${DB_DATABASE}` to the pgsql service, and Postgres only honours `POSTGRES_USER`/`POSTGRES_DB` during first-time `initdb`. Bring the stack up with no `.env` and they interpolate to empty strings: the cluster initializes as the default `postgres` role, and every later boot logs `Skipping initialization` and ignores the now-correct `.env` permanently. The symptom is `SQLSTATE[08006] … FATAL: password authentication failed … Role "konventix" does not exist` on `sail artisan migrate` — an authentication failure wearing a connection error's clothing, because 08006 is the connection-exception SQLSTATE class. Do not debug the network or `DB_HOST`; check `docker logs <pgsql> | head -1` for the skip line, and confirm with `psql -U postgres -l` that the role is absent. The only fix is re-running `initdb`: `docker compose down && docker volume rm konventix-poc_sail-pgsql && sail up -d`. Recreating the volume also re-runs `create-testing-database.sql`, which matters because a `testing` database left owned by `postgres` instead of the app role breaks the suite on table creation. Note this ordering trap is not obvious from `composer setup`: that script is what *creates* `.env`, so it cannot be the first thing you run on Docker.

## Dev stack mirrors production roles: one image, one container per role
compose.yaml runs each deployment role (web, queue, scheduler, reverb) as a separate service from the same Sail image via command override — mirroring ADR-0002/ADR-0025 production topology. Never mount docker.sock or spawn containers from the application; that is root-equivalent host access. Reverb is ONE shared server (browser: localhost:${FORWARD_REVERB_PORT}; backend: http://reverb:8080); brands become app entries in config/reverb.php, not extra processes. Host ports 8080–8083 clash with other local stacks on this machine — FORWARD_REVERB_PORT dodges that.

## Never add a compose profile — `sail` cannot reach one
`vendor/bin/sail` has no `--profile` handling anywhere in the script; grep it and you find only `SAIL_FILES`, which appends `-f` files to the `docker compose` invocation. A `profiles:` key therefore hides a service from the one command this project uses to drive the stack, and `COMPOSE_PROFILES` in `.env` only works when every developer remembers to set it. Garage (`s3`) and the k6 load stack (`load`) both lived behind profiles and were removed; everything in compose.yaml now starts on `sail up`. If a service must be optional, put it in a second compose file and reach it with `SAIL_FILES=compose.extra.yaml`, never a profile. A container that is meant to exit rather than serve (`k6`) gets a harmless default command plus `restart: 'no'`, the same shape as `migrate`.

## The k6 rush pushes to Prometheus; Grafana reads it, and the units are seconds
compose.yaml wires `K6_OUT=experimental-prometheus-rw` into the `k6` service so `docker compose run --rm k6 run /scripts/ticket-rush.js` needs no flags, with `prometheus` (remote-write receiver, empty `scrape_configs` — it scrapes nothing) as the sink and `grafana` provisioned from `contrib/grafana/` as the reader. Four things bite when editing the dashboard, all verified against k6 2.2.0 / Prometheus 3.7: metric names carry a type suffix and a unit change, so `http_req_duration` arrives as **`k6_http_req_duration_seconds`** even though k6's stdout summary prints milliseconds; there is no `k6_checks_total`, only the `k6_checks_rate` gauge; k6 never pushes a counter it did not increment, so a clean run has no `k6_server_errors_total` series at all and the panel needs `or vector(0)` to read 0 instead of blank; and `K6_PROMETHEUS_RW_STALE_MARKERS` marks every series stale the moment the run ends, so an instant query at `now` returns nothing once it is over — whole-run tiles must use `sum(max_over_time(<counter>[$__range]))`, which is also exact where `increase()` extrapolates (601.9 for 600 requests). Native histograms come from `K6_FEATURES=native-histograms` (the older `K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM` still works but logs a deprecation on every run) and need `--enable-feature=native-histograms` on the Prometheus side; they are what makes `histogram_quantile(0.95, sum(rate(k6_http_req_duration_seconds[$__rate_interval])))` a *windowed* p95, where k6's `K6_PROMETHEUS_RW_TREND_STATS` gauges compute over the whole run so far and only ever crawl upward. The dashboard is a diagnostic; `tests/Load/results/summary.json` from `handleSummary` stays the artefact `RushResultTest` asserts against.

## The rush runs against the production image via compose.prod-local.yaml, and two departures are forced
`compose.prod-local.yaml` runs the artifact from `Dockerfile` as its own compose project (`-p konventix-prod`) with its own volumes, which is where ROADMAP slice 24's owed rush belongs — the dev container is single-process and measuring it measures Sail. Two things about that rig cannot be "fixed", so do not try. **`APP_ENV=local`, not production:** `CommerceServiceProvider` registers `LocalHostedCheckoutAdapter` for the `null` settlement provider only outside production (ADR-0047 point 6) — in production the null provider honestly refuses to host a checkout, so the rush never reaches its checkout step and measures nothing past the shop page. A side effect worth knowing: `Model::shouldBeStrict()` keys off `isProduction()`, so the rig runs stricter than production, not laxer. **The fixture is seeded by the Sail image, not the artifact:** seeders use model factories, factories need `fakerphp/faker`, and faker is `require-dev` and deliberately absent from the image (ADR-0049 §1) — the fixture is rows in Postgres either way. Three traps that cost a run each: `routes/channels.php` builds the Pusher client at boot, so `REVERB_APP_ID`/`KEY`/`SECRET` must be present-and-empty (absent means `env()` returns null and Pusher's `string` parameter is a fatal TypeError on *every* artisan command, migrate included); the Sail image's entrypoint ends in `gosu $WWWUSER "$@"`, so driving it with plain `docker compose` instead of `vendor/bin/sail` needs `WWWUSER` set or gosu reads `php` as the username; and `konventix:install` must use the operator name and admin email `DatabaseSeeder` looks up (`Konventix Dev Operator`, `admin@konventix.test`) or the seeder creates a second operator beside it.

## A one-shot migrator role gates stack startup; AUTO_MIGRATE=false skips it
Fresh `sail up` used to crash-loop queue/scheduler/reverb with `relation "cache" does not exist` because those roles raced an unmigrated database. compose.yaml now runs a one-shot `migrate` service (Kubernetes-Job style) that every application role waits on via `depends_on: condition: service_completed_successfully`; pgsql/redis are gated on `service_healthy`. The service runs `php artisan konventix:migrate` — the gate lives in that command (`config('database.auto_migrate')` ← `AUTO_MIGRATE` env), inside the application image, so any deployment target (compose, a future K8s Job) reuses it identically. Operators disable it with `AUTO_MIGRATE=false` in `.env` — the command then exits 0 without touching the database, and migrations must be run manually (`sail artisan migrate`). Read the flag via config, never `env()` in the command, or `config:cache` in production silently breaks the gate.
