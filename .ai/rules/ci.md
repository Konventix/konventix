# CI

## The scanners are manual and advisory; the pipeline is verify, test, build, publish
Since the v0.6.4 release (pipelines 1828 and 1833, two days blocked on three SSRF findings in browser code) every scanner — `gitlab-advanced-sast`, `semgrep-sast`, `gemnasium-dependency_scanning`, `container_scanning` — and both gates — `scan:gate`, `scan:gate:image` — are `when: manual` with `allow_failure: true`, on the one anchor `*tier-scan` (merge requests, develop, main, tags) or its published-only twin for the two container jobs. `secret_detection` is the exception: it still runs on its own on every push, because it takes sixteen seconds and a README with a real key is the finding this fleet actually had — but it is advisory too, its verdict is the manual `scan:gate`. Nothing in the publishing chain waits for a scan: `publish:image` needs verify, analyse, test and `build:image`; `release:image` needs `publish:image`. A tag is therefore named as soon as its image is published, ~16 minutes, where a release tag used to wait 40-50.

What that means when you touch this file: a scanner or gate must keep both `when: manual` in every rule *and* an explicit `allow_failure: true` — the security templates set `false`, and a manual job that is not allowed to fail would block the pipeline while it waits to be played. Do not put a scanner back into `publish:image`'s or `release:image`'s `needs:`; the trade is recorded at the top of `.gitlab-ci.yml` and is the operator's to reverse, not a job's. The two SAST analyzers still share `gl-sast-report.json`, so press one per pipeline, never both, and press the scanners before the gate: a missing report fails the gate on purpose.

The old release tier (`*tier-release`, candidate and release tags only, the cross-file scan run automatically) is gone; the dev-tag pattern that kept semgrep off release tags with it. The sections below that describe the gates' bars, the analyzer's caches and the missing-report rule still hold — they describe what happens when the jobs are pressed.


## The security templates ignore merge requests unless AST_ENABLE_MR_PIPELINES is set
Every scanner's rules in `Jobs/Secret-Detection`, `Jobs/SAST`, `Jobs/Dependency-Scanning` and `Jobs/Container-Scanning` read `$AST_ENABLE_MR_PIPELINES == "true" && $CI_PIPELINE_SOURCE == "merge_request_event"`, and their remaining branches only match `$CI_COMMIT_BRANCH`. Since `workflow:` here creates no branch pipeline outside main, leaving the variable unset means the scans never see a merge request — they run on main, after the merge they exist to block, and the pipeline still looks green all the way through. Set it once at the top level, not per job.

Two related shapes on this instance (GitLab 19.3-ee, Ultimate): the new `dependency_scanning` job is `rules: [when: never]`, so `gemnasium-dependency_scanning` is the job that actually runs and the one to name in `needs:`; and `semgrep-sast` steps aside for the languages `gitlab-advanced-sast` covers once `GITLAB_ADVANCED_SAST_ENABLED` is on, so on a PHP/Vue commit only the advanced analyzer appears. Anything downstream must use `needs: [{job: …, optional: true}]` — which analyzers a commit produces depends on the files it touched, and a scanner that did not run is not a finding.

## The analyzers exit 0 with findings; scan:gate is what goes red (manually, since v0.6.4)
`allow_failure` on a scanner only covers the analyzer crashing. A report full of vulnerabilities is a successful job. `scan:gate` reads `gl-secret-detection-report.json`, `gl-sast-report.json` and `gl-dependency-scanning-report.json` and is the job that goes red: any secret at all, High and above for code and dependencies. Both gates are manual and advisory now (see the first section); what follows describes their verdict, which is unchanged.

The container report is judged in a **second** gate, `scan:gate:image`, and the reason it is a second job rather than a branch of the first is structural: `build:image` has `needs: [scan:gate]` and `container_scanning` needs `build:image`, so reading the container report inside `scan:gate` would close a `needs` cycle. That sibling runs on `*tier-release` only and `release:image` waits on it, so a critical OS CVE stops a promotion (#256) while develop, main and dev tags stay advisory — the base image's OS packages produce CVEs on their own schedule and must not be able to stop every merge in the repository.

**The two gates block at different severities, on purpose.** `scan:gate` blocks at High; `scan:gate:image` blocks at **Critical** and prints its High findings without failing. #256's criterion says Critical, and the asymmetry matches what each report is: `scan:gate` reads code and dependencies this repository owns and can fix, while the container report is mostly the Debian package set of the FrankenPHP base image, reported including CVEs Debian has not fixed. A stable base with zero High findings is the exception, so blocking there would mean the only way to cut a release is to edit `.gitlab-ci.yml` on the release branch. What the two gates do share is the waiver, and it is the only one either has: findings below the bar are printed and triaged in the merge request's security widget. There is no `vulnerability-allowlist.yml` in this repository and no `CS_SEVERITY_THRESHOLD` — setting the latter would make the analyzer the job that fails, which is exactly the division of labour above. Moving either bar, or adding an allowlist to either gate, is a decision recorded on #256 and applied with both gates in view.

**A finding only blocks when it can be acted on.** In both gates, a finding at or above the bar blocks when the report names a remediation and is printed as informational when it does not. The field is `solution` — gemnasium writes "Upgrade to versions 3.3.18, 5.1.6 or above.", the container analyzer writes an upgrade line only when a fixed package exists — so empty or absent means no fixed version was known when the report was written. The reason is pipeline 1674 (v0.5.4): `scan:gate:image` blocked the release on seventeen Criticals in `libsqlite3-0`, `libxml2`, `linux-libc-dev`, `perl`/`perl-base`/`perl-modules-5.36`, `libperl5.36`, `libaom3` and `zlib1g`, every one with an empty `solution`. Debian had no fixed package for any of them, so nothing anyone could merge would have turned that job green — the gate was not making a decision, it was holding the release hostage to a third party's schedule. The unfixed ones are still listed, under an explicit "unfixed, not blocking" heading with package, version and CVE id, and the summary line counts them ("17 Critical (0 with a fix, 17 without)") so a discriminator that quietly stops working is visible rather than silent. SAST is exempt from the rule and keeps the plain severity selection: a code finding has no third party to wait for, the fix is the change. The rule lives in both gates or in neither, like the severity bars.

One reporting trap worth knowing: the container-scanning report has **no** `name` key. The CVE id is in `identifiers[] | select(.type == "cve") | .value` and the package in `location.dependency`. Printing `.name` is what put a column of `null` next to every finding in pipeline 1674's log.

## dind needs plain TCP: these runners do not share the TLS cert volume
`DOCKER_TLS_CERTDIR: "/certs"` is the documented setup and it dies here on `Failed to initialize: unable to resolve docker endpoint: open /certs/client/ca.pem: no such file or directory`, before the job's first line — the runner config would have to mount `/certs/client` into the job container and does not. Use `DOCKER_HOST: tcp://docker:2375` with `DOCKER_TLS_CERTDIR: ""`. The daemon is only reachable on the job's own network. The same jobs also need `docker buildx create --driver docker-container`: the default `docker` driver cannot export `--cache-to type=registry`, and a retry on the same runner must fall through to `docker buildx use`.

## The pipeline runs at four depths, and a job's tier is one `rules: *tier-…` line
`develop` is the integration branch and the default; feature branches merge into it, it merges into `main` for a release. The anchors under `.tiers` decide where a job runs: `*tier-everywhere` (feature branch pushes included), `*tier-reviewed` (merge requests, develop, main, tags), `*tier-published` (develop onwards, wherever an image exists), `*tier-scan` (the same refs as reviewed, but `when: manual` on each — the scanners). Put a new job in the cheapest tier that can actually say something useful, and never reach for `$CI_DEFAULT_BRANCH` — it now means `develop`, so the release branch must be named literally.

The paragraph that follows predates the manual scanners and describes the rules the two SAST jobs had while they ran on their own; the "exactly one analyzer per pipeline" constraint is now the operator's to keep when pressing them.

Two consequences worth knowing. `semgrep-sast` and `gitlab-advanced-sast` both write `gl-sast-report.json`, so their rules are written to guarantee that **exactly one** of them appears in every pipeline — never both, which would leave the gate reading whichever landed last, and never neither, which would fail the gate on a report it could not find. Semgrep covers merge requests, develop, main and dev tags; the advanced analyzer covers candidate and release tags. A dev tag is matched exactly (`/^v?[0-9]+\.[0-9]+\.[0-9]+-dev(\.[0-9]+)?$/`, e.g. `v0.4.5-dev`, `v0.4.5-dev.2`): it is an image for a development instance and gets semgrep, so that cutting one off develop does not cost the twenty-four minute scan. A release candidate (`v0.4.5-rc.1`) is *not* cheap on purpose — it is what staging runs before the same commit ships — and an oddly named tag runs the full scan rather than silently skipping it. A push to main runs semgrep, not the advanced analyzer: the release tag follows on the same commit, and two copies of the scan on shared runners took 22 and 67 minutes on v0.4.4. Change either job's rules and re-check all eight pipeline shapes — feature branch, merge request, develop, main, dev tag, candidate tag, release tag, odd tag. And `scan:gate` runs on feature branches too, in a secrets-only mode (`GATE_SECRETS_ONLY`), because the other reports do not exist there; without that mode it would fail on the reports it could not find.

## gitlab-advanced-sast is bounded by its slowest rule group, and its two caches were never being hit
Analyzer v2.55.0 (pipeline 9683, v0.5.3, 50 minutes) splits the ruleset into as many groups as `--multi-core` — six of ~445 rules — and the job lasts as long as the slowest group: three groups took 8-10 minutes, three took 47-50. The split is balanced from `scan_metrics.csv` when a previous run's copy is in the cache and random otherwise, and the template keys that cache by ref with `$CI_DEFAULT_BRANCH` as fallback — develop never runs the job, so every tag logged "Failed to parse scan_metrics.csv, falling back to random chunking". Our job overrides `cache:key` to one constant so each tag inherits the previous tag's metrics; the sum of the six groups was 172 minutes of wall time, so a balanced split on six cores is under 30. The second cache is the taint-signature store `ts-cache.sqlite.gz` (`GITLAB_ADV_SAST_INCR_SCAN`): with it on, the analyzer looks back through previous commits for a pipeline carrying one and reanalyses only changed files, and a release tag is the same commit as its candidate. Both are measured on the next candidate/release pair, not before; the earlier note here — three passes of one rule each, 24 minutes, `-deep_inter_file` — described an older analyzer and no longer matches the log. Raising `--multi-core` beyond 6 is still not free: the other jobs share the host's eight cores. This is why the scan lives on the release tier: on the merge request loop it alone made a review take forty minutes. `SAST_EXCLUDED_PATHS` replaces the template default when set, so `spec, test, tests, tmp` is repeated in ours before the additions (docs, rules, contrib, stubs, storage, seeders, generated types).

## The image is built beside the verification and named after it: `publish:image` is the gate, not `build:image`
`build:image` carries `needs: []` and starts with the pipeline (#261). It builds, boots the artifact, checks the runtime php.ini and the bundle, and on a publishing pipeline pushes to `$UNVERIFIED_IMAGE` — `$CI_REGISTRY_IMAGE/unverified`, a path nothing deploys from. `publish:image` carries the `needs:` list that used to sit on the build (verify:format, verify:lint, analyse:php, analyse:js, test:php, test:js, scan:gate) and copies the manifest onto `$CI_REGISTRY_IMAGE:$IMAGE_SHA_TAG`, which is the first name a deployment can pull. So the rule "nothing reaches the registry unverified" now reads "no *deployable tag* exists unverified", and a red test leaves an image parked where nobody looks instead of blocking a build that was already free to run. Before the split the two longest jobs ran in series — the Pest suite, then ~830s of build — on every push to develop.

Three things follow. The staging tag is per commit, never per branch: two pipelines on develop at once would otherwise promote each other's image. That per-commit name has a consequence a release walks straight into — a tag and the push to main are the same commit and both publishing tiers, so both pipelines run `publish:image` for one `$IMAGE_SHA_TAG`, racing, and the loser finds the staging tag already promoted and deleted. It must therefore be idempotent: if the sha tag exists it says so and stops, because an earlier run of this same gated job put it there. v0.5.6 is what taught this (pipeline 1717) — `publish:image` failed on `unverified:sha-…: not found`, `release:image` was skipped behind it, and a released image had no semver name. `publish:image` deletes its staging tag afterwards through the registry API with `JOB-TOKEN` (which may only touch its own project), best effort, because the image is published by then and a tidy-up must not fail the pipeline. And `container_scanning` hangs off `publish:image` rather than the build, so it scans the tag that exists rather than the one that might not.

The cost is a runner slot held on suspicion, and the runners are the scarce resource. It is worth it because develop and tags run code a merge request has already verified, so the speculative build is almost never wasted. On a merge request `build:image` still only runs when the change could plausibly break it — the Dockerfile, `docker/`, either lockfile, `.dockerignore`, or `.gitlab-ci.yml`, which is the change most likely to break the build job itself and the one no other merge-request job would catch.

## `imagetools create` wraps a plain manifest in an index but copies an index as it stands
Both promote jobs (`publish:image`, `release:image`) name an existing image a second time with `docker buildx imagetools create`, and neither rebuilds. Whether the top-level digest survives depends on what the job is handed: a single-platform manifest comes back wrapped in an OCI index under a new digest, an index is copied unchanged. A null `revision` in the tags API is how you tell an index from outside.

Since #261 that wrap happens exactly once, in `publish:image`, so `release:image` copies an index and the release carries the same digest as its sha tag. Both eras are visible in the registry: `0.5.3` is `sha256:4afb57ac…` against its own `sha-33ce3925` at `sha256:c263ef9c…`, from when `release:image` wrapped a plain manifest itself, while `0.5.7` and `sha-f3c25e32` are both `sha256:a105f019…`. The comment on `release:image` claimed digest equality for months while it was false, then said it was impossible just as #261 made it true; it now describes the rule rather than one era. Nothing ever broke either way — the index points at the same manifest, same config, same layers — and every consumer here pins a tag, not a digest.

## Jobs that only *name* an image need no daemon: `.registry`, not `.docker`
`docker buildx imagetools` speaks to the registry directly and `docker login` stores credentials client-side, so the promote jobs take `.registry` (plain `docker:29.1.4-cli`) and skip the dind service and the buildx builder that `.docker` starts. Verified against docker:29.1.4-cli with no `DOCKER_HOST`: `imagetools inspect` answers normally and `login` fails on credentials rather than on a missing daemon. `.docker` stays for `build:image`, which genuinely builds.

## The CI image is the Dockerfile's `toolchain` stage, published from develop and main only
Jobs run on `$CI_REGISTRY_IMAGE/ci-toolchain:$TOOLCHAIN_TAG`, built with `--target toolchain` so the pipeline's PHP build, extension set and Node major are the ones that produce the release artifact. A merge request or a feature branch may create that tag when it is missing but never republishes it — one branch's Dockerfile experiment must not change the image every other pipeline runs on. Its own Dockerfile change is still proven, because `build:image` builds the whole file including that stage. If you change `toolchain` in a way every job must see at once, bump `TOOLCHAIN_TAG` in the same commit; a Dockerfile change alone republishes the tag only when it reaches develop or main.

## The image is published from GitLab only
`.github/workflows/image.yml` is gone (#255). It fired on pushes to `main` and `v*` tags — the same refs `.gitlab-ci.yml` guards — with no `needs` on `tests.yml` and none of the scanners, so anything `scan:gate` blocks could be published by pushing to the archived GitHub remote. Do not reintroduce a second publishing path; the chart pulls `registry.sxcs.de/konventix/konventix` and nothing pulls GHCR. `.github/workflows/tests.yml` stays: it publishes nothing.

## A job without a database pays ~40x on every `php artisan` boot
`.env.example` points `DB_HOST` at `pgsql` and `REDIS_HOST` at `redis` — the compose hostnames — and puts `CACHE_STORE`, `SESSION_DRIVER` and `QUEUE_CONNECTION` on redis. In a job with no such services those names do not resolve and every artisan start stalls on them. The controlled comparison, the same command in two jobs (the Vite plugin shells out to exactly `php artisan wayfinder:generate --with-form`): 246s in `verify:lint` with no services against 3.4s inside `test:php`, which has a postgres and a redis beside it; `key:generate` 30s against 0.7s. Pointing the service-less jobs at `127.0.0.1` — refused immediately, no timeout — with in-memory cache, session and queue took `verify:lint` from 358s to 88s and `verify:format` from 113s to 78s.

Anything new that runs artisan without services gets `variables: *offline-services`. The symptom to recognise is not an error: the job passes, just forty times slower, and it looks like the tool being slow rather than the network. It bites locally too, if `.env` names the compose hosts from outside the containers.

## eslint needs the generated routes, and it does not merely complain without them
`resources/js/{routes,actions,wayfinder}` are gitignored, so a fresh clone has none of them. Without them `import/order` cannot resolve `@/routes/...`, files it under the wrong group, and reports eighteen errors that are nowhere in the source — reproduced by moving the three directories aside and running `npx eslint .`. `vue-tsc` needs them too; vitest does not, because `vitest.config.ts` is deliberately standalone. `verify:lint` generates them once (`--with-form` matches `formVariants: true` in vite.config.ts) and hands them on as an artifact; `test:php` does not take that artifact, because `npm run build:ssr` runs the generator itself and standing alone beats waiting for the job that produces it.

## A docs/ branch runs the documentation shape: the guard and secret detection, nothing else
`workflow:rules` sets `PIPELINE_SHAPE=docs` when the merge request's source branch or the pushed branch starts with `docs/`; every tier anchor and the four hand-ruled jobs (`prepare:toolchain`, `semgrep-sast`, `build:image`, `scan:gate`) read the variable first and step aside, `scan:gate` in its secrets-only mode. What stays is `docs:only` — a diff against the merge request's base (the merge-base with develop on a bare push) that fails on any changed file outside `docs/`, `.ai/`, `*.md` and `LICENSE` — and `secret_detection`, because a README with a real key is the finding the fleet repository actually had. The branch name is the only switch and the guard is what makes it safe: code on a docs/ branch turns the pipeline red with the files named, it never merges unverified. It is the ninth shape to re-check when a job's rules change. A change to `.gitlab-ci.yml` itself is not documentation — it belongs on a ci/ branch, where the full merge request pipeline proves it.
