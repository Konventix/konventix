# Release 0.8.1 — cutover-critical bugs (2026-09-22)

Scope settled with the operator on 2026-09-22 after the 0.8.0 rollout: the
bugs that stand between the platform and the cutover, nothing else. Work goes
directly on `develop`, one commit per task, each closing its GitLab issue.
xpertise on dev is **dropped from this release** by operator decision.

Already on develop: the support dialog scrolls on a phone (c8adf4e, reported
by the operator on 2026-09-22, no issue).

## Task 1: A new brand can issue tickets (#287) — Admission, Platform

**The bug:** nothing creates an entrance signing key when a brand is created,
so the first ticket download of every brand is a 500 for the buyer, and the
error names `admission:rotate-signing-key`, a command that does not exist.

- [ ] A brand gets an active key at creation: a listener on the brand-created
      event (Admission's side of it — Admission must not import Platform's
      model), idempotent, plus a backfill on the deploy path so existing
      brands without a key get one. `konventix:install` covers a fresh
      install; the backfill must be safe to run on every deploy.
- [ ] `admission:rotate-signing-key {brand?}` with `--all` for every brand
      without an active key; it is what the exception message already tells
      the operator to run, so the message becomes true rather than changing.
- [ ] `docs/operations.md`: what the key is, when to rotate it, what breaks
      while it is missing.
- [ ] Test: a ticket download for a brand created a moment ago answers 200.

## Task 2: The waiting room stops burning quota on cookie-less clients (#221) — Commerce

**The bug:** a client that keeps no cookie loops `/shop` → `/waiting-room` →
`/shop`, mints a ticket each round and spends the five-per-IP-per-hour budget
in seconds; `curl -L` locked a test IP out for an hour. The 429 that follows
is a blank page with no `Retry-After` and no explanation.

- [ ] A client that cannot hold the cookie does not loop: the second arrival
      without a readable ticket must not mint a second one. Reuse the ticket
      it was just handed (one-shot token in the redirect) or detect the
      missing cookie and answer the waiting room page directly.
- [ ] The cap refuses with `Retry-After` (seconds until the window opens) and
      a page that says what happened and when to come back, not a bare 429.
- [ ] Neither change touches the size of the cap (#133 owns that) or
      `TRUSTED_PROXIES` (#178).
- [ ] Tests: a cookie-less walk spends at most one ticket; the refusal
      carries `Retry-After` and the page names the wait.

## Task 3: Cart writes take their locks in one order (#233) — Commerce, Registration

**The bug:** four cart actions write `cart_lines` first and lock the parent
`carts` row afterwards. On PostgreSQL the foreign key takes `FOR KEY SHARE`
on the parent for every child write, and `Cart::touchExpiry()` raises the same
row to `FOR NO KEY UPDATE` at the end — two concurrent transactions on one
cart deadlock. Two more unordered multi-row locks are the same class of bug.

- [ ] Lock the parent `carts` row **before** the first write to `cart_lines`
      in `PlaceRegistrationLineInCart`, `AddProductToCart`,
      `ChangeCartLineQuantity` and `RemoveCartLine`; `OpenCart::for()` runs
      outside the transaction, so two concurrent settlement requests of one
      buyer resolve the same cart and must serialise on it.
- [ ] `ExpireCarts` reads the cart's lines in a deterministic order and locks
      `ProductVariant` rows in that order, not in heap order.
- [ ] The quota locks order their rows: `ConsumesQuotas`, `ReleasesQuotas`,
      `PromoteFromWaitlist`, `ExpireWaitlistOffers` and
      `RegistrationType::quotas()`.
- [ ] Tests that would have caught it: concurrent writes on one cart, and two
      registrations on two types sharing two quotas.

## Task 4: Removing a cart line asks first, and says the right thing (#219, #220, #211) — Commerce, Registration, Messaging

**Three bugs on one path.** Removing a line cancels the registration behind it
in the same click, with no confirmation and no undo (#219). The cancellation
mail then calls it `cart_expired` although the buyer removed it and the cart
was still valid (#220). And a cart that expires cancels even a **confirmed**
registration, which quietly voids a seat somebody already holds (#211).

- [ ] Removing a line that carries a registration asks first and names the
      consequence. Scope decided by the operator — see the decision note
      below.
- [ ] `CancelPendingRegistrationForCart` takes the reason from the trigger:
      `CartLineExpired` stays `cart_expired`, `CartLineRemoved` becomes its
      own code, and the cancellation mail says "you removed it from your
      cart" rather than "expired". The listener passes the event through.
- [ ] A registration in state `confirmed` is **not** cancelled by an expiring
      cart line: it is left standing, logged, and reported to the operator.
      Submitted and approved registrations expire as they do today. This is
      the default the issue itself names; ADR-0057 point 5 agrees.
- [ ] Tests per trigger: reason code and mail text for expiry vs removal, and
      a confirmed registration surviving an expired cart line.

## Task 5: The Reverb key is documented (#224) — konventix-helm, docs

**Not a code bug.** The empty `REVERB_APP_KEY` in the ConfigMap is deliberate:
under `REVERB_APP_PROVIDER=brands` the apps come from the brand rows
(ADR-0025), and the ConfigMap ships the variable present-and-empty because the
application wants it at boot. Only the runbook is missing.

- [ ] `docs/operations.md`: how a brand's `reverb_app_key`/`reverb_app_secret`
      are generated and rotated, what a page shows while they are absent, and
      the `brands` vs single-app provider choice.
- [ ] The chart's `values.yaml` comment points at that runbook.
- [ ] Close #224 with the design note, since criterion 1 asks for a value the
      design deliberately leaves empty.
