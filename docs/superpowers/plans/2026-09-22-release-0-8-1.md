# Release 0.8.1 — cutover-critical bugs (2026-09-22)

Scope settled with the operator on 2026-09-22 after the 0.8.0 rollout: the
bugs that stand between the platform and the cutover, nothing else. Work goes
directly on `develop`, one commit per task, each closing its GitLab issue.
xpertise on dev is **dropped from this release** by operator decision.

Already on develop: the support dialog scrolls on a phone (c8adf4e, reported
by the operator on 2026-09-22, no issue).

## Task 1: A new brand can issue tickets (#287) — Admission, Platform

**The bug:** nothing creates an entrance signing key when a brand is created,
so the first ticket download of every brand is a 500 for the buyer, and the
error names `admission:rotate-signing-key`, a command that does not exist.

- [x] A brand gets an active key at creation: a listener on the brand-created
      event (Admission's side of it — Admission must not import Platform's
      model), idempotent, plus a backfill on the deploy path so existing
      brands without a key get one. `konventix:install` covers a fresh
      install; the backfill must be safe to run on every deploy.
- [x] `admission:rotate-signing-key {brand?}` with `--all` for every brand
      without an active key; it is what the exception message already tells
      the operator to run, so the message becomes true rather than changing.
- [x] `docs/operations.md`: what the key is, when to rotate it, what breaks
      while it is missing.
- [x] Test: a ticket download for a brand created a moment ago answers 200.

## Task 2: The waiting room stops burning quota on cookie-less clients (#221) — Commerce

**The bug:** a client that keeps no cookie loops `/shop` → `/waiting-room` →
`/shop`, mints a ticket each round and spends the five-per-IP-per-hour budget
in seconds; `curl -L` locked a test IP out for an hour. The 429 that follows
is a blank page with no `Retry-After` and no explanation.

- [x] A client that cannot hold the cookie does not loop: the second arrival
      without a readable ticket must not mint a second one. Reuse the ticket
      it was just handed (one-shot token in the redirect) or detect the
      missing cookie and answer the waiting room page directly.
- [x] The cap refuses with `Retry-After` (seconds until the window opens) and
      a page that says what happened and when to come back, not a bare 429.
- [x] Neither change touches the size of the cap (#133 owns that) or
      `TRUSTED_PROXIES` (#178).
- [x] Tests: a cookie-less walk spends at most one ticket; the refusal
      carries `Retry-After` and the page names the wait.

## Task 3: Cart writes take their locks in one order (#233) — Commerce, Registration

**The bug:** four cart actions write `cart_lines` first and lock the parent
`carts` row afterwards. On PostgreSQL the foreign key takes `FOR KEY SHARE`
on the parent for every child write, and `Cart::touchExpiry()` raises the same
row to `FOR NO KEY UPDATE` at the end — two concurrent transactions on one
cart deadlock. Two more unordered multi-row locks are the same class of bug.

- [x] Lock the parent `carts` row **before** the first write to `cart_lines`
      in `PlaceRegistrationLineInCart`, `AddProductToCart`,
      `ChangeCartLineQuantity` and `RemoveCartLine`; `OpenCart::for()` runs
      outside the transaction, so two concurrent settlement requests of one
      buyer resolve the same cart and must serialise on it.
      (`Actions\Concerns\LocksTheCartBeforeItsLines`, one lock taker for all
      four, inside each Action's own transaction; the three product paths keep
      `product_variants` ahead of `carts`.)
- [x] `ExpireCarts` reads the cart's lines in a deterministic order and locks
      `ProductVariant` rows in that order, not in heap order. (Lines in the
      `position` order `Cart::lines()` declares; the variants in one locking
      pass in `product_variants.id` order, which also holds *between* two
      carts holding the same variants at opposite positions.)
- [x] The quota locks order their rows: `ConsumesQuotas`, `ReleasesQuotas`,
      `PromoteFromWaitlist`, `ExpireWaitlistOffers` and
      `RegistrationType::quotas()`. (One `orderBy('quotas.id')` on the
      relation, which `SubmitRegistration::guardQuantity()` and
      `ReduceRegistrationQuantity` inherit too.)
- [x] Tests that would have caught it: concurrent writes on one cart, and two
      registrations on two types sharing two quotas. (`CartLockOrderTest`,
      `QuotaLockOrderTest` — the lock *order* asserted from the query log
      rather than a raced pair of connections, which RefreshDatabase's
      wrapping transaction makes impossible to write without a second process
      and a timing window; both files say so in full.)

## Task 4: Removing a cart line asks first, and says the right thing (#219, #220, #211) — Commerce, Registration, Messaging

**Three bugs on one path.** Removing a line cancels the registration behind it
in the same click, with no confirmation and no undo (#219). The cancellation
mail then calls it `cart_expired` although the buyer removed it and the cart
was still valid (#220). And a cart that expires cancels even a **confirmed**
registration, which quietly voids a seat somebody already holds (#211).

- [x] Removing a line that carries a registration names the consequence and
      is undoable. Scope decided by the operator — an undo window, not a
      confirmation dialog. Removal stays one click; a registration line is
      *soft*-removed (`cart_lines.removed_at`), so nothing irreversible
      happens inside the window — the registration and its hold stay alive,
      `Cart::lines()` filters the line out of the page, the totals, the
      badge and the checkout, and `CartRemovedLines.vue` offers it back
      through `POST /cart/lines/{line}/restore`. A product line still
      deletes on the click and gives its stock back. The window rides the
      cart's own `expires_at`, so no second sweep exists: `ExpireCarts`
      closes an unused one and `ResolveRemovedCartLines` closes it at
      checkout, and both emit `CartLineRemoved` then — so a removal nobody
      undid still ends in a cancelled registration and released quota.
- [x] `CancelPendingRegistrationForCart` takes the reason from the trigger:
      `CartLineExpired` stays `cart_expired`, `CartLineRemoved` becomes its
      own code, and the cancellation mail says "you removed it from your
      cart" rather than "expired". The listener passes the event through.
      (`Registration\Enums\CartHoldEnded`, a required argument with no
      default; `de`/`en` template branch, no PHP expression, prepared
      payload field only.)
- [x] A registration in state `confirmed` is **not** cancelled by an expiring
      cart line: it is left standing, logged, and reported to the operator.
      Submitted and approved registrations expire as they do today. This is
      the default the issue itself names; ADR-0057 point 5 agrees. Reported
      through the channel the module already has — a counter,
      `confirmed_registrations_kept_total{brand,trigger}`, with a stat and a
      timeseries on the Sale dashboard; no alert, because a held seat with an
      open receivable is the dunning ladder's business, not a pager's.
- [x] Tests per trigger: reason code and mail text for expiry vs removal, and
      a confirmed registration surviving an expired cart line.
      (`CartLineCancellationTest` rewritten — the test that pinned the
      one-click cancellation now pins that nothing is cancelled —
      `RegistrationMailsTest`, `RegistrationMetricsTest`, `CartTest`,
      `CartCheckoutTest`.)

## Task 5: The Reverb key is documented (#224) — konventix-helm, docs

**Not a code bug.** The empty `REVERB_APP_KEY` in the ConfigMap is deliberate:
under `REVERB_APP_PROVIDER=brands` the apps come from the brand rows
(ADR-0025), and the ConfigMap ships the variable present-and-empty because the
application wants it at boot. Only the runbook is missing.

- [x] `docs/operations.md`: how a brand's `reverb_app_key`/`reverb_app_secret`
      are generated and rotated, what a page shows while they are absent, and
      the `brands` vs single-app provider choice.
- [x] The chart's `values.yaml` comment points at that runbook.
- [x] Close #224 with the design note, since criterion 1 asks for a value the
      design deliberately leaves empty.

No rotate command for the Reverb credentials exists; rotating is a manual
column update that drops the brand's connected clients. Documented as such,
and a command is a candidate for a later release rather than this patch.

## Task 6: A theme export is a theme file somebody can author from (operator ask 2026-09-22) — Platform

**The gap:** `ExportBrandTheme` writes out `Brand::themeTokens()` and
`darkThemeTokens()`, which hold the brand's **overrides** and nothing else. A
brand on the default theme therefore exports an almost empty file. Handed to a
designer or a coding agent it says nothing: not which tokens exist, not what
they mean, not what the defaults are, and not which pairs have to clear the
BFSG contrast the import enforces — so the first file they write back is
refused by `UpdateBrandTheme` for reasons the file never mentioned.

- [ ] The export carries an **effective value for every catalogue token**,
      light and dark: the brand's override where it has one, `TokenCatalog`'s
      default where it does not. Exporting a brand that has themed nothing
      yields the complete default theme.
- [ ] The file says what each token is: at least the catalogue's label and
      group per token, and the contrast pairs the import will check. This is
      the part that makes it authorable by somebody who has never seen the
      editor. Keep it a separate block from the values, so it reads as
      reference rather than as something to edit.
- [ ] An import of the new file still works, and an import of an **old**
      file still works. Decide and write down whether the envelope stays
      `konventix.brand-theme/v1` or becomes `v2` accepted alongside v1 — the
      test `an import of an export changes nothing` must stay true.
- [ ] Say in the file itself which values were the brand's own overrides, so
      round-tripping does not quietly turn a brand that follows the defaults
      into one that has frozen all of them. Whether that is a marker per token
      or a list beside the maps is the implementer's call.
- [ ] Tests: a brand with no overrides exports every catalogue token with the
      catalogue's defaults; a brand with two overrides exports those two plus
      the defaults for the rest and marks which were its own; round-tripping
      an export changes nothing; an old file still imports.

## Task 7: A saved brand theme actually renders (operator report 2026-09-22) — Platform

**The bug, found on dev:** `sxlan` had a full custom palette saved, the editor
preview showed it, `sxlan.dev.konventix.de` served a correct
`<style id="konventix-brand-tokens">` block — and the site stayed default. A
pod restart changed nothing because nothing was cached: the block was emitted
**above** `@vite`, and `resources/css/app.css` declares the very same raw
tokens on `:root` at the same specificity. The stylesheet loaded second and
won. Every brand theme this platform has ever saved has been inert on the
brand's own site.

- [x] The block is emitted after `@vite`, so the brand's values are the last
      declaration on `:root`.
- [x] The stale `TODO(brand)` in that template, which claimed the middleware
      did not exist yet, is replaced by why the position matters.
- [x] Test: the brand block's offset in the rendered document is greater than
      the last stylesheet link's. Asserting that the tokens are *present*
      never caught this and could not have.
