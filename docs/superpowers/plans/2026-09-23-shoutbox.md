# Shoutbox Implementation Plan (0.9.0, sub-project D)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An admitted participant opens the live hub and finds the room talking; an organizer can remove a line, mute someone for ten minutes with a reason they can read, or lock the wall.

**Architecture:** Five tables in Community — rooms with a subject, messages with soft deletion, timed mutes, reports, and a durable admission-badge projection. Connection state and room activity live in Redis and are never persisted. Realtime over Reverb on a private per-room channel, copying the notification bell's proven path. Access is the hub's gate; moderation is a capability that does **not** require admission.

**Tech Stack:** Laravel 12 modules (`app-modules/community`), Pest on Postgres, spatie/laravel-data + typescript-transformer, Inertia v3 + Vue 3 + shadcn-vue, Laravel Echo + pusher-js against Reverb, Redis, Laravel Pennant.

**Spec:** `docs/superpowers/specs/2026-09-23-shoutbox-design.md` (D-COM-01..09) and **ADR-0067**, which settles the two Community SPEC reversals this work depends on.

### Task 1: The model — rooms, messages, mutes, reports

**Requirements:** spec **§4.1–§4.4**.

**Files:** four migrations; `src/Models/{Room,Message,RoomMute,MessageReport}.php` + factories; `src/Enums/{RoomSubject,ReportState}.php`; `tests/ShoutboxModelTest.php`.

**Interfaces produced:** `RoomSubject::{Event,Match,Competition}` (backed `event|match|competition`; `Match` and `Competition` ship unused, per ADR-0067 — the schema is ready, the subjects wait on B); `ReportState::{Open,Resolved,Dismissed}`; `Room` with `unique(subject_type, subject_id)`, `locked_at`, `closed_at`; `Message` with soft-delete columns (`deleted_at`, `deleted_by_user_id`, `deleted_reason`) and `index(room_id, id)`; `RoomMute` with a **NOT NULL `reason`** and nullable `expires_at`; `MessageReport` with `unique(message_id, reporter_user_id)`.

**Tests:** a second room for the same subject is refused; a mute without a reason is refused by the database, not only by validation; a message longer than 500 characters is refused; the same reporter cannot report one message twice; `Message` ordering by `id` is chronological (two messages created in sequence come back in order).

### Task 2: The admission badge projection

**Requirements:** spec **§4.5** and **§5**, ADR-0067 decision 2.

**Files:** migration for `community_event_presence`; `src/Models/EventPresence.php`; `src/Listeners/ProjectAdmissionBadge.php`; provider registration; `tests/AdmissionBadgeTest.php`.

**Interfaces produced:** `EventPresence` (`event_id`, `user_id`, `checked_in`, `last_direction`, `unique(event_id, user_id)`).

**Listens to** `Konventix\Admission\Events\{ParticipantAdmitted, ParticipantPresenceChanged, ParticipantHubAccessEnded}`. Copy `ProjectEventParticipation`'s shape for the gate and the `forceFill` — it is the in-module precedent.

**Read this before writing the listener:** sub-project B hit a trap here that cost it a review round. Do **not** assume which Admission event carries which fact — open the emit sites and check. In particular `AdmissionIssued` sets `holder_user_id` **null** for every registration-derived admission; the holder is named later. You are consuming A's *participant* events rather than Admission's raw admission events, which sidesteps that entirely — but verify, do not assume.

**Tests:** an admitted participant gets `checked_in = true`; an `out` scan flips `last_direction` and leaves `checked_in` alone; `ParticipantHubAccessEnded` clears the badge; replaying any of them twice changes nothing; with `community` off for the brand no row is written.

### Task 3: Writing and moderating — Actions, Data, events, rate limits

**Requirements:** spec **§6**, **§9**, D-COM-01/04/08/09.

**Files:** `src/Data/{PostMessageData,MuteData,ReportData}.php`; `src/Actions/{PostMessage,RemoveMessage,MuteParticipant,UnmuteParticipant,LockRoom,UnlockRoom,ReportMessage,ResolveReport}.php`; `src/Events/{ShoutboxMessagePosted,ShoutboxMessageRemoved,ShoutboxMessageReported}.php`; `src/Enums/Permission.php` gains `ModerateCommunity`; the named rate limiter in the provider; `tests/ShoutboxWriteTest.php`, `tests/ShoutboxModerationTest.php`.

**Interfaces produced:** `PostMessage::handle(Room $room, string $authorUserId, PostMessageData $data): Message`; `MuteParticipant::handle(Room $room, string $userId, string $byUserId, string $reason, ?int $minutes): RoomMute`; the three events, **carrying no body text**.

**The rules that must be enforced in the Action, not only the UI:** 5 messages per 10 seconds per person per room; the 500-character cap; a muted person is refused while `expires_at` is in the future or null; a locked or closed room refuses every post. A client that ignores the UI must still be refused.

**Tests:** the sixth message in ten seconds is refused; a muted person is refused and the refusal names the reason and the remaining time; the mute expires and posting resumes; a locked room refuses posting and still reads; removal leaves a tombstone that a report still resolves against; each of the three events fires once with no body in the payload.

### Task 4: Realtime and presence

**Requirements:** spec **§5** (connection and room axes), **§8** (transport).

**Files:** `src/Broadcasting/RoomChannel.php` + the `routes/channels.php` entry; `src/Presence/ConnectionState.php` (Redis, TTL'd); broadcast on `ShoutboxMessagePosted`/`ShoutboxMessageRemoved`; `tests/ShoutboxBroadcastTest.php`.

**Interfaces produced:** a private per-room channel authorised only for a participant admitted to that room's event; `ConnectionState` with `online(string $userId): void`, `forRoom(string $roomId): array` — Redis keys with a TTL, **no table**.

**Copy the notification bell's path**: `NotificationReceived` implements `ShouldBroadcastNow` and broadcasts on a private channel that `routes/channels.php` authorises. Do not invent a second pattern.

**Tests:** channel authorisation refuses a member who is not admitted to that event; a posted message broadcasts once on the room's channel; nothing about connection state is written to any table (assert the table count, not just the absence of a model).

### Task 6: Retention, gating, GDPR, observability, docs

**Requirements:** spec **§7**, **§12 items 7–10**, ADR-0059.

**Files:** `src/Listeners/CloseRoomOnEventConcluded.php`; `src/Console/SweepExpiredRoomsCommand.php` + `registerSchedule()`; `CommunityGdprHandler` extended; `src/Metrics/CommunityMetrics.php` + recorder + a panel in `contrib/observability/src/`; `SPEC.md` amended per ADR-0067; `TODO.md`; `docs/operations.md`; `tests/ShoutboxRetentionTest.php`, `tests/ShoutboxActivationTest.php`.

**Interfaces produced:** `community:sweep-shoutbox`, scheduled daily with `withoutOverlapping()`; metric `community_messages_posted_total{brand}`.

**GDPR is not optional and is specified:** export carries the subject's own messages and their own reports; erasure **removes** their messages outright (a shoutbox line is not a business record) and **anonymises** `reporter_user_id` on reports they filed, which stay as facts about the message. `community_event_presence` rows are exported and deleted with the subject. There is an in-repo precedent for the anonymise-not-delete half: `ResourcesGdprHandler` nulls `holder_user_id` rather than dropping the row.

**SPEC amendment:** apply ADR-0067's two changes to `app-modules/community/SPEC.md`, each citing the ADR — the purpose sentence gains event-scoped rooms, the presence sentence gains the "displayed, never enforced" badge exception. Do not silently rewrite; quote the ADR.

**Tests:** `EventConcluded` closes the room and it stops accepting posts; the sweep deletes messages, mutes and reports 30 days later and keeps the room tombstone; GDPR export and erasure do exactly the four things above; with `community` off there are no routes, no card, no listeners and no errors.
