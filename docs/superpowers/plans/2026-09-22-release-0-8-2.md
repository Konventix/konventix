# Release 0.8.2 — money and reconciliation (2026-09-22)

The second patch release of the 0.8.x line, scoped with the operator after
0.8.1 shipped: the money paths that can leave a buyer or the books wrong.
Work goes directly on `develop`, one commit per task, each closing its issue.

## Operator decisions, taken 2026-09-22

- **D-0.8.2-1 (#7):** a partial credit note is expressed by **picking lines and
  quantities**, not by typing a gross sum. Each selected line is computed
  through `TaxCalculator`, which is the only shape that is exact when an
  invoice mixes tax rates.
- **D-0.8.2-2 (#8):** a promoted waitlist registration is priced at **the price
  it was submitted at**, not the price at promotion. The registrant pays what
  they saw when they joined the queue.
- **D-0.8.2-3 (#250):** a manual refund with no provider reference gets a
  **`payment_reversals` row with a synthetic reference `manual:<order>`**.
  `provider_reference` stays NOT NULL (decision of 2026-09-08) and the unique
  key stays the table's convergence mechanism; everything that already reads
  reversals sees the manual case with no second mechanism.
- **D-0.8.2-4 (#249):** the valve clocks count from **the first failed attempt**,
  stamped in a new column, not from `orders.created_at`.
- **Not asked, assumed (#244):** the VAT switch stays where it is, on the
  operator (`Operator::small_business_scheme`). Only the buyer-facing label is
  wrong and only the label is fixed. A per-brand VAT status would be a schema
  change and its own issue; say so if brands under one operator really differ.

## Task 0: Verify and close #187 — no code expected

`RecordRefund` already emits `OrderLineCancelled` with
`REASON_ORDER_REFUNDED` per registration line of a **whole** refund of a cart
order, and `CancelRegistrationOnOrderLineCancelled` cancels and releases the
quota. A **partial** refund deliberately releases nothing (D-REG-15, and the
0.8.0 partial-cancellation work is the path that does release units).

- [ ] Prove it with a test that walks a whole refund of a multi-line cart order
      end to end, if no such test exists yet; close #187 with the evidence, or
      reopen the gap if the walk disproves the reading above.

## Task 1: The waitlist sweep and the promoted price (#8) — Registration

- [x] `registration:expire-waitlist-offers` runs with `withoutOverlapping()`,
      like `commerce:expire-carts`.
- [x] A promoted `on_payment` registration is priced at submission
      (D-0.8.2-2): the waitlist entry carries the price declaration it was
      created with, and promotion settles at that, not at the type's current
      price. **The tax class is pinned with the amount**, not re-read: a
      `TaxClass` is a class and never a rate, so Commerce still resolves the
      rate and the treatment (§19, reverse charge) at settlement whatever
      travels in the pin — re-reading the class would freeze no law, would
      let a later reclassification reach back into a promise, and on a
      gross-displaying type would charge a gross the registrant never saw.
      Argued in `RequestSettlement`'s docblock.
- [x] Tests: a promotion after a price rise and after a price cut both settle
      at the submitted price; the sweep does not overlap itself.
