# Release 0.8.2 — money and reconciliation (2026-09-22)

The second patch release of the 0.8.x line, scoped with the operator after
0.8.1 shipped: the money paths that can leave a buyer or the books wrong.
Work goes directly on `develop`, one commit per task, each closing its issue.

## Operator decisions, taken 2026-09-22

- **D-0.8.2-1 (#7):** a partial credit note is expressed by **picking lines and
  quantities**, not by typing a gross sum. Each selected line is computed
  through `TaxCalculator`, which is the only shape that is exact when an
  invoice mixes tax rates.
- **D-0.8.2-2 (#8):** a promoted waitlist registration is priced at **the price
  it was submitted at**, not the price at promotion. The registrant pays what
  they saw when they joined the queue.
- **D-0.8.2-3 (#250):** a manual refund with no provider reference gets a
  **`payment_reversals` row with a synthetic reference `manual:<order>`**.
  `provider_reference` stays NOT NULL (decision of 2026-09-08) and the unique
  key stays the table's convergence mechanism; everything that already reads
  reversals sees the manual case with no second mechanism.
- **D-0.8.2-4 (#249):** the valve clocks count from **the first failed attempt**,
  stamped in a new column, not from `orders.created_at`.
- **Not asked, assumed (#244):** the VAT switch stays where it is, on the
  operator (`Operator::small_business_scheme`). Only the buyer-facing label is
  wrong and only the label is fixed. A per-brand VAT status would be a schema
  change and its own issue; say so if brands under one operator really differ.

## Task 1: The waitlist sweep and the promoted price (#8) — Registration

- [x] `registration:expire-waitlist-offers` runs with `withoutOverlapping()`,
      like `commerce:expire-carts`.
- [x] A promoted `on_payment` registration is priced at submission
      (D-0.8.2-2): the waitlist entry carries the price declaration it was
      created with, and promotion settles at that, not at the type's current
      price. **The tax class is pinned with the amount**, not re-read: a
      `TaxClass` is a class and never a rate, so Commerce still resolves the
      rate and the treatment (§19, reverse charge) at settlement whatever
      travels in the pin — re-reading the class would freeze no law, would
      let a later reclassification reach back into a promise, and on a
      gross-displaying type would charge a gross the registrant never saw.
      Argued in `RequestSettlement`'s docblock.
- [x] Tests: a promotion after a price rise and after a price cut both settle
      at the submitted price; the sweep does not overlap itself.

## Task 2: The §19 label on the buyer's side (#244) — Commerce, Registration

- [x] `taxNote()` in `purchaseTexts.ts` distinguishes
      `TaxTreatment::SmallBusiness`: no "incl./excl. VAT" where no VAT is
      charged, but "no VAT charged (§ 19 UStG)" instead. It is keyed on the
      **resolved treatment**, never on a zero rate — a rate of "0.00" is an
      amount and the election is a status, and a reverse charge produces the
      first without the second. `EndPriceData` already carried the fact as
      `includesTax`, which was `treatment === Standard` and so also false
      for a reverse charge; renamed to `smallBusinessScheme` and computed
      from `TaxTreatment::SmallBusiness`.
- [x] Every surface that shows a price: `ShopLandingCard.vue`,
      `shop/Index.vue`, `shop/Show.vue`, `EventOffers.vue` (through
      `OfferPrice.vue`). No prop per page: the fact travels on the payload
      that carries the price — `ShopProductData` for the three shop
      surfaces, `EndPriceData` for the contributed offers — and the shop
      pages' and landing slot's own `smallBusinessScheme` page prop is gone.
      The other `taxNote()` callers the grep found are fixed the same way:
      `cart/Show`, `cart/Confirm` (the §312j (3) BGB button's own page) off
      the cart preview's calculation, and `pay/Show`, `pay/Order`,
      `pay/Confirm`, `commerce/my/Show` off the order's `tax_treatment`
      snapshot. A *reverse-charged* order still reads "incl. VAT" on those
      last four — separate wording decision, now in Commerce's backlog.
- [x] Tests, including a vitest on the pure `taxNote()` (gross, net, the
      scheme, and that the note is never printed by default), plus feature
      tests on the shop surfaces and the event offers with the scheme on and
      off.

## Task 4: A closed dispute closes its reversal (#249) — Commerce

- [x] `StripeReversalCatchUp` and the reconcile sweep close an open reversal
      when Stripe reports the dispute `won`, `lost` or `warning_closed`, with
      the same outcome the webhook would have produced (ADR-0057 point 7).
      The agreement is structural rather than promised: the status map is one
      constant, `StripeReversalCatchUp::CLOSING_STATUSES`, which
      `StripeWebhookController::disputeClosed()` now reads too, and the
      transition is `RecordPaymentReversal`'s in both paths. A closing status
      only closes a row this deployment already holds `Open`; a `lost`
      dispute we never heard of is still recorded from scratch (#235), and a
      `won` one is still skipped. The moment handed to the Action for a
      closure is *now*, never the dispute's `created`, or `repay_due_on`
      would land in the past and the deadline sweep would cancel the order
      with no days at all. `warning_closed` reaching a record at all is a
      change to the webhook too — it used to be acknowledged and dropped,
      which left the same permanent `Open` row.
- [x] The valve clocks count from the first failed attempt (D-0.8.2-4):
      `orders.first_failed_attempt_at` (migration
      `2026_09_22_120000_add_first_failed_attempt_at_to_orders_table`),
      stamped once by `RecordPaymentFailure` and never moved, read by
      `HostedPaymentProbe::holdExpired()`. The clock is the **later** of that
      stamp and the order's payment window, so the fallback for rows that
      predate the column is exactly today's behaviour — and fix round 3's
      F-1 ("both clocks start at the end of the payment window", which a
      retried cart order depends on) is not silently reverted.
- [x] Tests: a lost `charge.dispute.closed` for a won dispute closes the
      reversal and treats the receivable as the webhook would; a second run
      changes nothing. Also the lost and `warning_closed` directions, the
      won dispute we never heard of, and four valve tests in
      `ExpireRegistrationOrdersTest` (full grace from today's first failure,
      fallback with no stamp, a stale stamp that must not shorten the valve,
      and the stamp written once).

## Task 6: Partial credit notes with line-level tax (#7) — Commerce

The largest task of the release and the one the rest is sequenced around.

- [x] `IssueCreditNote` takes selected lines and quantities (D-0.8.2-1) and
      computes net, tax and gross **per line** through `TaxCalculator`, rather
      than inheriting the invoice's allocation for a gross sum.
      `Data\CreditNoteLineSelectionData` is the pick — a line id and a whole
      quantity, never an amount — and `Actions\ResolveCreditNoteLines` runs
      each one through the new `TaxCalculator::lineAtRate()` at the **order
      line's snapshotted rate** (ADR-0017), never a re-resolution of its
      `TaxClass`: an order credited next year is credited at the rate it was
      charged at. Rounding stays the calculator's own — per line, half-up to
      cents at intermediate scale 4, then summed — so the totals are exactly
      the sum of the printed lines and no second policy exists beside it.
      Part of a single unit is **not supported** and is refused with a named
      error rather than approximated: splitting a unit's net by a fraction
      would put an unverifiable figure on a document that cannot be
      corrected (ADR-0031).
- [x] The credit-note PDF shows the credited subset correctly, including an
      invoice that mixes tax rates. `credit_note_lines` is the credit note's
      own snapshot of what it credits, so the renderer still never reads
      `Order`/`OrderLine`: the Blade template prints the subset line by line
      the way the invoice does, with each line's own rate and a per-rate
      breakdown wherever more than one rate is credited, and the Factur-X
      half carries one position per line and one `BG-23` tax group per rate.
      A credit note that names no lines — a whole-invoice one, and every row
      issued before the table existed — keeps the summary position and the
      rate derived from its two totals, which is exact where there is
      nothing to allocate.
- [x] The sum of all credit notes against one invoice can never exceed its
      gross — enforced, tested, and refused rather than clamped. **And no
      line is credited beyond what was sold**, which is the stricter half:
      an invoice of 200.00 + 100.00 still has room at the total level once
      its first line is credited whole, so only the per-line ledger can
      refuse spending that room on the same line again. Both guards run
      inside the transaction that draws the number, and `RefundOrder` asks
      once more **before** the provider call so a refusal never leaves money
      returned with no Gutschrift to explain it.
- [x] The console gains the line-and-quantity picker
      (`components/admin/OrderRefundDialog.vue`, extracted from
      `admin/orders/Show.vue`, which keeps the page inside the size rule);
      the existing callers keep working and were the regression surface.
      `RefundUnitsOnRegistrationQuantityReduced` (D-REG-15) now states its
      refund as a selection like every other caller instead of carrying its
      own copy of the calculator's arithmetic — same numbers, one rounding
      policy, and its units join the per-line ledger so a later console
      partial cannot send them back twice. `IssueCreditNote` still accepts
      explicit totals for the whole-invoice credit note (a full refund, an
      ADR-0036 transfer, ADR-0057 point 4's cancellation).
- [x] Unblocks #73.
